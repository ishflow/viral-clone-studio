# viraleditor robustness (Task C6, 2026-10-05)

What happens when things go wrong: a render's parent dies, a worker dies mid-job, the disk is full, a font is gone, media is broken or odd, many jobs in a row, tools that hang or flood, tests under load. Base tree `4d23bfd`. The regression net is `viraleditor/src/robust/` (green for what holds; `it.fails` with `FINDING <n>` for what does not).

Commands: `cd viraleditor && pnpm vitest run src/robust src/adapters/exec.test.ts` (fast) and `VE_RENDER=1 pnpm vitest run src/robust` (real HyperFrames 0.8.120, Chrome, ffmpeg 8.1.1). Media in the tests is made by ffmpeg in temp folders.

## Findings, most severe first

IDs: `F5`–`F9` are the `FINDING <n>` of the `it.fails` tests; each has a green twin `FINDING <n> (today)` that pins what happens now, so a broken fixture cannot pass as a confirmed finding. (F8 and F9 were fixed in C6b: their tests are ordinary passing tests now.)

- **F1. Chrome outlived every killed render (fixed).** The CLI's process group does not hold Chrome: puppeteer launches it `detached`, in a group of its own. A render that hit its time limit, or a parent that got SIGTERM, left 5 `chrome-headless-shell` processes for 2–3 minutes each. Fix in `adapters/exec.ts`: `killGroupOf` lists every process under the group leader (one `ps -A -o pid=,ppid=`, while the leader lives) and kills those too. Tests: `exec.test.ts` "on a timeout also kills a grandchild that left the group", "SIGTERM to the process: a grandchild in a group of its own is gone too"; `robust/process.render.test.ts` (SIGTERM and limit cases failed first with 5 Chrome left, run against the old `exec.ts`).
- **F9. SIGTERM to the worker killed the job it promised to wait for (fixed in C6b).** `exec.ts` registers its own SIGTERM handler for killGroup children and kills them at once, so the render died and the loop stopped the run as engine-error: a service restart ended the user's run for good. Now `worker/main.ts` (`exitOnSignals`) answers SIGINT/SIGTERM with `handBack()`: in the signal handler, before the render's death is seen, the run is released (`runs.release`: still `running`, `claimed_by` and `heartbeat` NULL, so the next claim takes it without the 60 s wait); the handler runs `asOwner` (F8), so nothing it writes afterwards reaches the run; the process exits 0 once the loop has unwound, after 10 s (`GRACE_MS`) at the latest. The job is redone by the next worker, not finished by this one (finishing would need exec.ts's hook to spare the children while a worker handles the signal). SIGKILL path unchanged. Test: `robust/shutdown.test.ts` (child exits 0, run handed back, a restarted worker finishes it); `worker/loop.test.ts` (handBack).
- **F8. A worker that lost its run could still finish it (fixed in C6b for the run's row; F8b open).** The loop now runs every handler inside `runs.asOwner`: `beat`, `setSteps`, `setVariants`, `finish` and `stop` of that run change it only while `claimed_by` is still this worker; otherwise they change nothing, return false and record the code `not-owner` (`not-running` when the run ended), and the loop logs `run <id>: not-owner`. Callers' signatures are unchanged, so prepare / edit / scan are covered without edits; produce already had its own owner-checked writes (`produce/rows.ts`). The test job publishes its video only while `runs.holds` the run. **F8b (open, outside C6b's paths):** `produce/assemble.ts` renders into the variant folder and renames `final.mp4` without an owner check, and two workers render into the same `rendered` name there; the move into place needs `holds(db, runId, claimedBy)` right before the rename (and a per-worker temp name). Tests: `robust/worker.test.ts`, `db/runs.test.ts`, `worker/loop.test.ts`.
- **F10. Other adapters started children without `killGroup` (fixed in C6b).** `adapters/llm.ts` (the `claude` CLI), `adapters/downloader.ts` and both calls in `scan/shorts.ts` (yt-dlp, which starts ffmpeg) now pass `killGroup: true`, so a timeout (or the end of the process) ends what the tool started. Tests: one each in `llm.test.ts`, `downloader.test.ts`, and two in `scan/shorts.test.ts` (a stub that starts `sleep 30` and waits): red before (the grandchild lived), green after.
- **F5. HDR source normalized quietly with the wrong transfer (open).** This ffmpeg has `tonemap` but neither `zscale` nor `libplacebo`; `normalize` reads a PQ/BT.2020 10-bit clip as BT.709 and tags the result BT.709: washed-out colour, no error. `checkInputs` warns `media-colour` and advises normalize, which then does this. Test: `robust/media.test.ts` (`it.fails`). Proposal: refuse `smpte2084` / `arib-std-b67` in normalize with a code of its own (needs a new `MediaErrorCode` and a line in `cli/translate.ts`).
- **F6. A variable-rate source passes `checkInputs` (open).** `quality/inputs.ts` reads `fps` (r_frame_rate, 30) and never `constantRate`; frame numbers of such a clip are not its times (74 frames counted in 2.97 s). `measure.streams` reports `constantRate: false` correctly and normalize makes it constant. Test: `robust/media.test.ts` (`it.fails`). `src/quality/**` belongs to Task C1b at the moment.
- **F4a. `media.probe` accepted a file cut short (fixed).** With its index first (faststart), half a file probed as 720×1280, 3 s, 44 frames, exit 0 (ffprobe printed "partial file" on stderr); normalize then produced a 46-frame 1.5 s clip quietly. `measure.streams` already refused it. Fix: `media.probe` reads the same damage words on stderr → `not-media`. Test: `robust/media.test.ts`.
- **F4b. Rotation metadata ignored (fixed).** A phone clip stored 1280×720 with a 90° rotation was described as 1280×720 by `media.probe` and `measure.streams`, while ffmpeg (normalize, picture) and Chrome show it 720×1280; `measure.picture` returned a 1280-wide picture of a 720-wide frame (same byte count: no error). Fix: `shownSize` in `media.ts`, used by both adapters. Test: `robust/media.test.ts`. The first version of this fix also fed the shown size to normalize's matrix guess for untagged clips (HD is 709, SD is 601), so a turned 640x480 clip read as 480x640 was guessed 709: rgb (40,140,70) came out (32,126,68). The guess now reads the stored size (fix round 1; test "an untagged SD clip turned by rotation metadata keeps its colour"). The guess stays orientation-dependent for clips stored in portrait (an untagged 480x640 frame counts as 709), as before this task.
- **F2. Output floods were kept whole (fixed).** Without `onData`, `runProcess` kept all output; a 100 MB flood became a 100 MB string, and past V8's longest string (~512 M characters) `stdout + d` would throw inside the data handler (assumed from V8's limit, not run). Fix: `OUTPUT_LIMIT` (64 M characters a stream) stops the child with `ExecError('output-limit')`. media, measure, renderer, transcriber and the command line map it to their `tool-failed`; `aligner.ts` mapped every ExecError but a timeout to `not-installed`, the wrong cause: now `align` gives `tool-failed` and `ready` names the real error (only a binary that cannot start is "not installed"). Tests: `exec.test.ts`, `robust/limits.test.ts`, `aligner.test.ts` "a tool that floods its output".
- **F3. Transcriber timeout left the recogniser running (fixed).** `transcriber.ts` ran the CLI without `killGroup`. Test: `transcriber.test.ts` "a timeout also ends what the CLI started".
- **F4c. A relative file name that starts with `-` (fixed).** ffprobe took it as an option (`tool-failed`, "Missing argument for option"). Fix: the ffprobe calls in `media.ts` and `measure.ts` pass the resolved path. Test: `robust/media.test.ts`.
- **F4d. A render target whose folder cannot be made threw a raw `EACCES` (fixed).** `renderer.render` now wraps the folder, removal and sweep in a `RenderError`. Test: `robust/disk.test.ts`.
- **F11. SIGKILL of a render's parent is not handled by us (low).** Nothing of ours can run; the CLI died within 2 s here only because its next progress line hit the closed pipe. A silent phase of the CLI would run to its end. Test: `robust/process.render.test.ts` (SIGKILL, green).
- **F12. A killed render leaves the CLI's work folders (low).** `work-<uuid>-*` and `.<name>.<pid>-<id>.render.hf-transaction-*` beside the target (`sweepStale` matches only our own `.mp4` temp names), and Chrome's profile and `hf-de-verify-*` in TMPDIR. The next CLI render into the same folder removed the folders beside the target (seen, twice). Large when a long render dies in a folder that is never rendered into again. Seen in the case 1 runs; no test.
- **F15. Tests under load (fixed, test timing).** `exec.test.ts` "kills the group exactly once" needs ~3.4 s by construction and took 4.4 s alone at load 100: past the 5 s default together with other files (3 of 3). The two hook tests polled 10 s inside a 5 s test and read the pid file as soon as it existed. Explicit 30 s limits and a non-empty read. The ledger's other suspects did not fail in 3 runs at load 70–107.
- **F7. A font missing at render time (low).** `check` names the missing woff2; `render` alone succeeds with a fallback face. Every render path we have checks first (`produce/assemble.ts`, the command line's `render`). Test: `robust/font.render.test.ts` (`it.fails`).
- **F14. A disk-full render has no code of its own (low).** It is a `RenderError` whose message carries "No space left on device"; `MediaError` is `tool-failed`. Test: `robust/disk.test.ts`.
- **F13. A 0.1 s sound reads as −70 LUFS (low).** ebur128 has no 400 ms block to gate; `checkInputs` would call an audible short sound `audio-silent` (a warning). Seen in the case 5 run; no test.
